# 🎯 和为 K 的子数组：从滑动窗口误区到全解法通关指南

在力扣中，**560. 和为 K 的子数组**是一道极其经典的“羊皮狼”题目。很多人一看到“连续子数组”、“和为 K”，就会条件反射地掏出滑动窗口，结果直接撞得头破血流。

本篇文档将带你彻底认清这道题的底层逻辑，并提供从**标准通用版**到**极致性能优化版**的全部 Java 解法。

---

## ⚠️ 惊天大坑：为什么这道题绝对不能用滑动窗口？

滑动窗口能用的核心前提是：**区间具备单调性**（即右指针右移，和一定变大；左指针右移，和一定变小）。
但是，这道题的题目提示中明确指出：**数组元素可能为负数，也可能为 0**！
* 如果右边进了一个负数，窗口的和反而变小了。
* 如果左边移走一个负数，窗口的和反而变大了。

这直接导致指针的移动方向完全失控。因此，滑动窗口在有负数的情况下**彻底作废**。

---

## 🚀 第一重境界：前缀和 + HashMap（通用标准最优解）

既然滑动窗口废了，我们需要掏出另一件绝门武器：**“前缀和”** 加上 **“逆向查账（哈希表）”**。

### 🎮 大白话核心机制
1. **什么是前缀和？**
   雇一个会计从左往右走，每走一步就把一路上所有数字加起来。这个累计的总分就叫**前缀和（`preSum`）**。
   如果从位置 $A$ 走到位置 $B$，$B$ 的累计和是 22，$A$ 的累计和是 15。那么中间这一段子数组的和就是 $22 - 15 = 7$。
2. **灵魂公式的逆向思维**
   我们要找的是中间某一段和等于 $K$ 的子数组。
   `现在的累计和 (preSum) - 过去的某一时刻的累计和 = K`
   移项变形：**`过去的某一时刻的累计和 = 现在的累计和 (preSum) - K`**！
3. **哈希表是干嘛的？**
   哈希表就是会计手里的一本账，用来记录：**“每一个累计和，在过去一共出现了多少次？”**
   每走到一个位置，算出当前的 `preSum` 后，直接去账本里查：**“以前有没有哪几次，累计和刚好等于 `preSum - K`？”** 如果有，直接把过去的出现次数加进最终答案。

### 💻 Java 代码实现
```java
import java.util.HashMap;
import java.util.Map;

public class SolutionCommon {
    public int subarraySum(int[] nums, int k) {
        if (nums == null || nums.length == 0) return 0;

        // 1. 记账本：Key 存过去的前缀和，Value 存这个前缀和出现了几次
        Map<Integer, Integer> map = new HashMap<>();
        
        // 💡 极其重要的初始化：如果刚好一出发累计和就等于 K，我们需要减去 0。
        // 相当于比赛还没开始，我们的初始得分就是 0，并且这个 0 已经默认存在 1 次了。
        map.put(0, 1);

        int preSum = 0; // 当前的累计前缀和
        int count = 0;  // 满足和为 K 的子数组总个数

        // 2. 会计开始从左往右走，只扫一遍数组
        for (int num : nums) {
            preSum += num; // 实时累计现在的总分

            // 3. 逆向查账：看看过去有没有哪几次的累计和，刚好等于 (preSum - k)
            if (map.containsKey(preSum - k)) {
                count += map.get(preSum - k); // 以前出现过几次，就说明现在能凑出几种答案
            }

            // 4. 把现在的累计和也登记到账本里，供后面的数字查阅
            map.put(preSum, map.getOrDefault(preSum, 0) + 1);
        }

        return count;
    }
}
```
*   **时间复杂度**：$O(N)$，哈希表查账是 $O(1)$，只扫一遍。
*   **空间复杂度**：$O(N)$，最坏情况下哈希表要存 $N$ 个不同的前缀和。

### ⚠️ 易错点：查账表达式别写反了

很容易顺手写成 `map.containsKey(k - nums[i])`，这是把**前缀和查账**和**两数之和**的套路搞混了：

| | 正确写法 | 错误写法 |
| :--- | :--- | :--- |
| 表达式 | `map.containsKey(preSum - k)` | `map.containsKey(k - nums[i])` |
| 含义 | 在历史**前缀和**里找 `preSum - k` | 在历史**元素值**里找 `k - nums[i]` |

**记忆口诀**：map 的 key 空间是**前缀和**，所以查的也必须是前缀和，永远用 `preSum - k`，跟 `nums[i]` 无关。

## ⚡ 附加彩蛋：如果面试官突然追加限制“全是正数”？

如果在面试进行到一半，面试官微笑着对你说：“*噢，对了，如果我限定这个数组里**全部都是正整数**呢？*”

请注意，一旦全是正数，数组就重新具备了“越加越大”的**单调性**。这意味着我们**可以抛弃前缀和，重新启用滑动窗口**！

### 💻 全正数下的最优解（空间降为 O(1)）
```java
public class SolutionAllPositive {
    public int subarraySum(int[] nums, int k) {
        // 只有当数组全是正数时，才能开启纯粹的滑动窗口
        int left = 0, sum = 0, count = 0;
        
        for (int right = 0; right < nums.length; right++) {
            sum += nums[right]; // 扩张窗口
            
            // 当窗口和大于 k 时，疯狂收缩左边界
            while (sum > k && left <= right) {
                sum -= nums[left];
                left++;
            }
            
            // 刚好相等，抓到一个连续子数组答案
            if (sum == k) {
                count++;
            }
        }
        return count;
    }
}
```
*   **降维打击**：此时空间复杂度直接从 $O(N)$ 暴跌到了 **$O(1)$**！不需要任何哈希表和额外大数组，只用两个指针在原数组上蹦跶，在空间上对前缀和解法实现了无情碾压。

>
> 不过，在实际工程落地中，我们可以根据具体的业务数据特征做进一步的性能优化：
> 1. 如果业务数据提示**前缀和的上下界是明确且有限的**，我会选择用 **`int[]` 数组外加 `Offset` 偏移量**来完全替代 `HashMap`，从而消除 Java 包装类自动装箱的堆内存开销，实现硬件级的寻址效率。
> 2. 如果业务场景能确保**输入序列全是正整数**，那么该问题将重新具备单调性。此时我会立刻放弃前缀和方案，**将其重构为纯双指针的滑动窗口**，直接将算法的空间复杂度从 $O(N)$ 压缩到物理级别的 **$O(1)$**。”
