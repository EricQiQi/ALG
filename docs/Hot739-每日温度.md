# LeetCode 739. 每日温度

对应源码：[Hot739_dailyTemperatures.java](../src/s12_stack/Hot739_dailyTemperatures.java)

## 题目描述

给定每日温度数组 `temperatures`，返回数组 `answer`，其中 `answer[i]` 表示第 `i` 天之后要等几天才能遇到更高的温度。如果之后都不会升高，则 `answer[i] = 0`。

```
[73,74,75,71,69,72,76,73] → [1,1,4,2,1,1,0,0]
[30,40,50,60]             → [1,1,1,0]
[30,60,90]                → [1,1,0]
```

## 💡 大白话解析

暴力解法是每天往后扫一遍找第一个更高的温度，O(n²)。单调栈把它降到 O(n)。

**栈里存的是「还在等更高温度的日子」。**

站在第 `i` 天的角度想：我今天能帮谁结算答案？只能帮那些**温度比我低、而且还没被结算过**的日子。而这些日子恰好有一个漂亮的性质——它们在栈里是**从栈顶往下连续排列**的。

为什么连续？因为栈内温度始终保持递减：如果某天 A 比它上面压着的某天 B 温度高，那 A 早就在 B 入栈时就被结算弹走了，不可能还留在 B 下面。

于是算法变成一句话：

> **新来一天，把栈顶所有比它矮的日子一次性削平（结算），然后自己入栈等着。**

两个设计要点：

| 要点 | 为什么 |
| :--- | :--- |
| 栈里存**下标**而不是温度值 | 答案要算天数差 `i - preIndex`，光有温度算不出距离 |
| 用 `res` 数组的默认值 0 兜底 | 遍历完还留在栈里的日子 = 后面再也没升温 = 答案就是 0，一行都不用写 |

## 图解

以 `[73,74,75,71,69,72,76,73]` 为例（下图显示温度便于阅读，实际栈里存的是下标）：

```
i=0  73   [73]
i=1  74   [73] → 73 结算，等 1 天 → [74]
i=2  75   [74] → 74 结算，等 1 天 → [75]
i=3  71   [75, 71]              ← 71 比 75 矮，只能先压着等
i=4  69   [75, 71, 69]          ← 继续压着
i=5  72   [75, 71, 69] → 69 结算(等1天)、71 结算(等2天) → [75, 72]
i=6  76   [75, 72] → 72 结算(等1天)、75 结算(等4天) → [76]
i=7  73   [76, 73]
─────────────────────────────────────────────────────────
结束      栈剩 76、73 没人能结算 → res[6]=res[7]=0（数组默认值）
          最终：1 1 4 2 1 1 0 0
```

看 `i=5` 和 `i=6` 两行：**一次入栈可以连续结算掉多个之前的日子**，这就是 `while` 而不是 `if` 的原因。

## 💻 Java 代码实现

```java
public int[] dailyTemperatures(int[] temperatures) {
    int n = temperatures.length;
    int[] res = new int[n];   // 默认全 0，恰好对应"之后没有更高温度"

    Deque<Integer> stack = new ArrayDeque<>();   // 单调递减栈，存下标
    for (int i = 0; i < n; i++) {
        // 当前温度比栈顶那天高 → 栈顶那天等到答案了，弹出结算
        while (!stack.isEmpty() && temperatures[stack.peek()] < temperatures[i]) {
            int preIndex = stack.pop();
            res[preIndex] = i - preIndex;        // 等待天数 = 下标之差
        }
        stack.push(i);                           // 当前这天入栈，等着被后面结算
    }
    return res;   // 栈中剩余下标的 res 保持 0
}
```

## 复杂度分析

| 指标 | 复杂度 | 说明 |
| :--- | :---: | :--- |
| 时间 | O(n) | 虽然有嵌套 `while`，但**每个下标最多进栈一次、出栈一次**，总操作数 ≤ 2n |
| 空间 | O(n) | 最坏情况（温度严格递减，如 `[50,40,30]`）栈里存下全部 n 个下标 |

那个 `while` 看着像 O(n²)，其实是**均摊 O(1)**：出栈的总次数不可能超过入栈的总次数 n。这是单调栈复杂度分析的标准套路。

## ⚠️ 易错点

### 1. 栈里存下标，不是温度值

```java
Deque<Integer> stack;   // 存 i
stack.push(i);          // ✓
stack.push(temperatures[i]);   // ✗ 后面算不出天数差
```

### 2. 比较时要"解引用"：`temperatures[stack.peek()]`

栈里是下标，直接拿 `stack.peek()` 去和 `temperatures[i]` 比，比的是下标和温度，逻辑全错。

### 3. 是 `while` 不是 `if`

一天可能同时结算掉多个之前的日子（见图解 `i=6`：76 一口气结算了 72 和 75）。写成 `if` 只能弹一个，剩下的永远卡在栈里。

### 4. 用严格 `<`，不是 `<=`

题目要的是**更高**温度，相等不算。实测 `[70,70,70]` → `[0,0,0]`。若写成 `<=`，第二天会把第一天结算成"等 1 天"，错。

### 5. `!stack.isEmpty()` 必须写在 `&&` 前面

空栈时 `peek()` 返回 `null`，`temperatures[null]` 会 NPE。依赖短路保护——和 [有效的括号](Hot20-有效的括号.md) 易错点 3 是同一个坑。

### 6. 别忘了栈里剩余的元素

它们的 `res` 靠数组默认值 0 兜底。如果用 `List` 或手动 `new int[n]` 后填过其他值，就必须显式补 0。

## 🧠 单调栈方法论

「找左边/右边第一个比它大（小）的元素」这类问题，都是单调栈的信号：

| 特征 | 对应写法 |
| :--- | :--- |
| 找右边第一个**更大** | 正向遍历 + 单调**递减**栈（本题） |
| 找右边第一个**更小** | 正向遍历 + 单调**递增**栈 |
| 找左边第一个更大 | 反向遍历 + 单调递减栈 |
| 需要算**距离/宽度** | 栈里存**下标** |
| 只比大小不关心位置 | 栈里可以存值 |
